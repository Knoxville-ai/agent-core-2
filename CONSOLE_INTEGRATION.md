# Console integration — agent-core (openclaw vessel)

This document is the contract between this image and the
knoxville-ai-console. The v0.3 rewrite collapses the previous
role-catalog runtime into a general-purpose openclaw vessel that the
console provisions per-agent.

## Architectural shift from v0.2

| Concern | v0.2 (Python/FastAPI) | v0.3 (openclaw vessel) |
| --- | --- | --- |
| Runtime | Custom Python agent loop + capability registry | `openclaw` agent (Node) |
| Role logic | `roles/<slug>/` in this repo + `app/runtime/capabilities_builtin.py` | openclaw skills installed into `~/.openclaw/workspace/skills/` |
| Config delivery | Env vars + Storage blobs read by Python bootstrap | Env vars + Storage blobs rendered into `openclaw.json` + `workspace/*.md` by the shim at boot |
| HTTP surface | `/api/v1/conversations/:id/messages` (SSE) + `/interrupt` + `/files` | **same surface** — wire-compatible |
| Native channels | Telegram bot loop in `app/messaging/` | None — disabled in `openclaw.json` |

The console-side messaging proxy (`src/lib/messaging-proxy.ts`,
`src/app/api/org/[orgId]/messages/[conversationId]/stream/route.ts`,
`/interrupt/route.ts`) requires **no changes** to talk to v0.3 agents.

## Provisioning contract

The console provisions an agent by:

1. Creating a Railway service for an org, pointing at this image
   (`ghcr.io/<repo>:<tag>` from the `roles.source_repo` /
   `roles.source_image_tag` columns or per-agent BYOA overrides).
2. Setting the env vars listed below.
3. Uploading optional workspace blobs to Supabase Storage under
   `agent-data/orgs/{org}/agents/{uid}/memory/`.
4. Pointing a `*.up.railway.app` domain at port `8080`.

### Required env vars

| Var | Source in console code | Notes |
| --- | --- | --- |
| `AGENT_UID` | `provisioning.ts:buildAgentEnvVars` | `sha256(TELEGRAM_BOT_TOKEN)[:16]` (or `sha256(random)[:16]` for vessel agents) |
| `AGENT_ORG` | same | org id |
| `AGENT_ROLE` | same | `generic` for vessel agents (other slugs reserved for legacy role agents) |
| `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` | env | Storage access |
| `SUPABASE_JWT_SECRET` | env | shared HS256 secret used to verify caller bearers |
| `OPENCLAW_GATEWAY_TOKEN` | `generateGatewayToken()` | already generated by the console today |
| `LLM_PROVIDER` / `LLM_MODEL` / `LLM_API_KEY` | model picker | written into `openclaw.json` |

### Optional env vars (new for v0.3)

| Var | Purpose |
| --- | --- |
| `PLATFORM_MCP_URL` | URL of the platform's MCP server. Set this to give the agent an outbound channel to discover and converse with other platform agents (drive-throughs) AND to fetch its own bundle at boot. |
| `PLATFORM_API_TOKEN` | per-agent bearer (`knox_agent_*`) for the platform MCP. Required whenever `PLATFORM_MCP_URL` is set. |

When both are set, the shim's `renderWorkspace()` adds an entry to
`mcp.servers.knoxville_platform` in `openclaw.json`, and at boot the
agent calls `get_my_bundle` on the same MCP to discover which Drive
Through capabilities route to it. Each capability's pinned clawhub
skill is installed (or re-installed) into `workspace/skills/` via
`openclaw skills install <ref> --version <version> --force` — the
directory is wiped first so a capability removed from the bundle goes
away. Each capability's `promptFragment` is appended to
`workspace/SOUL.md`, and every `required: true` envVarSpec is validated
against `process.env`. Boot fails loud on a clawhub install failure, a
skill version conflict, or a missing required cred.

Editing a Drive Through capability and restarting the agent is the
only step needed to pick up new skills, new prompt fragments, or
removed capabilities — the boot pipeline reconciles from scratch.

When unset, the agent is purely inbound: no outbound A2A, no bundle, no
capability-driven skill installs. The vessel still boots with whatever
prompt blobs the console uploaded to Storage.

## Bring your own agent (BYOA)

A third party can list a self-hosted drive thru whose agent runs on their
own infrastructure. The console proxies each conversation turn to the
owner's endpoint, authenticating with an owner-set shared secret. An
openclaw vessel already satisfies the BYOA endpoint contract (the HTTP
surface above is a superset of it) — so a BYOA listing can point at an
openclaw gateway URL directly, or at any other stack that implements the
same tiny surface. The full wire contract lives in
[`BYOA.md`](./BYOA.md); the console renders a user-facing version at
`/drive-throughs/byoa`.

## Storage contract (unchanged from CONTRACT.md)

The shim reads/writes the same paths the console already manages:

```
agent-data/orgs/{org}/agents/{uid}/
├── manifest.json          ← shim writes on every boot
├── memory/
│   ├── system_prompt.md   ← shim → workspace/SOUL.md (read-only at boot)
│   ├── identity.md        ← shim → workspace/AGENTS.md
│   ├── boot.md            ← shim → workspace/TOOLS.md
│   └── playbook.md        ← shim → workspace/playbook.md (writable by agent)
├── config/                ← reserved for future skill-level policies
├── state/                 ← agent-owned; shim does not touch
└── logs/                  ← agent-owned; shim does not touch
```

The `manifest.json` written by v0.3 includes a `vessel` block:

```json
{
  "agent_uid": "…",
  "role": "generic",
  "org_id": "…",
  "created_at": "…",
  "last_boot": "…",
  "bootstrap_version": 1,
  "vessel": { "kind": "openclaw", "image_version": "0.3.0-openclaw.0" }
}
```

The `vessel.kind` field lets the console distinguish v0.2 and v0.3 agents
when rendering role-specific UI.

## HTTP surface (port 8080)

Identical to v0.2 for the endpoints the console actually calls:

| Method + path | Behavior |
| --- | --- |
| `POST /api/v1/conversations/:id/messages` | Body: `{ "text": "…" }`. Response: `text/event-stream` with events `delta` / `tool_call` / `tool_result` / `done` / `error`. Verified by `Authorization: Bearer <Supabase session.access_token>` against `SUPABASE_JWT_SECRET`. |
| `POST /api/v1/conversations/:id/interrupt` | Aborts the in-flight turn. Returns `{ ok: true }` on success, `{ ok: false, error }` on gateway failure. |
| `GET  /healthz` / `/readyz` | Liveness / readiness. `/readyz` returns 503 until the openclaw gateway WebSocket is connected. |
| `*    /api/v1/agents/:uid/files/...` | Returns 501 (file attachments are not yet implemented for vessel agents). The console should treat 501 the same as "not supported on this agent." |

## Migration strategy

The v0.3 image deploys side-by-side with v0.2:

1. Tag the v0.3 image as `0.3.0-openclaw` (or similar).
2. Add a `generic` row to `public.roles` with:
   - `source_repo = 'knoxville-ai/agent-core'`
   - `source_image_tag = '0.3.0-openclaw'`
   - `capability = 'telegram_chat'` (placeholder — unused by vessel)
   - `kind = 'task'`
   - empty `policy_schema` / `default_policies`
3. Existing role-bound agents (`ap_invoices`, `ebay_listings`, etc.)
   keep running on whatever `source_image_tag` they were provisioned with
   (typically `0.2.x`).
4. New "vessel" agents are provisioned by selecting the `generic` role.
5. Role logic that needs to come along will be ported to openclaw skills
   one role at a time. Skills are dropped into `workspace/skills/` and
   either:
   - baked into a custom vessel image variant (`agent-core-finance:0.3.x`),
   - or pulled from Supabase Storage at provision time (future).

Until porting finishes, both image versions are first-class citizens.
